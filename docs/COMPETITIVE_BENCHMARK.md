# 竞争评测与开发验收约束

状态：设计与验收规范，2026-10-23。本文没有新增测试结果，也不启动 benchmark、采购算力、调用收费 API 或修改产品运行代码。数值例子是待评测计划冻结的候选设置，不是性能承诺。

## 1. 产品目标与成功条件

产品定位：**预算内、近数据、CPU 原生的预测工作流**。

服务已有 PostgreSQL 数据、缺少专门 ML 平台和算法经验、希望利用受控 CPU 资源完成预测验证与 SQL 使用的用户。源表可为 GB 乃至 TB，不能据此宣称同等体量的稠密训练矩阵可以在短时间内完成训练。原始数据量、实际扫描量、特征工作集和预测批量必须分别报告。

竞争价值必须由实际证据支持，不能由“库内”“C 实现”“无 GPU”或“算法数量”推导。优先证明至少一类可重复的价值：

- 质量达标时，首次可用 pipeline 的端到端时间或 CPU 总消耗更低。
- 同一预先规定的资源预算内，预测质量或合格任务完成率更高。
- 相同业务预测工作负载下，额外数据副本、运行内存、常驻依赖或数据库干扰更少，同时满足质量和延迟门槛。

目标是形成清楚的质量—代价折中优势，不要求在所有数据集、模型、资源维度同时获胜，也不得只展示有利任务。部署简单不能替代质量合格；更快但质量不达标不算成功。

### “质量接近”的可检验定义

每种任务在执行前指定主质量指标、方向、业务最低门槛、允许退化 delta 及不确定性估计方法。

- 对越大越好的指标：Q_ours >= Q_reference - delta。
- 对越小越好的误差：E_ours <= (1 + epsilon) * E_reference；参照接近零时使用预定绝对容差而非不稳定比值。
- Accuracy、AUROC、PR-AUC、log loss、MAE、RMSE 不能共用一个“1%差距”。分类百分点与相对误差必须明确单位。
- 示例候选：AUROC 绝对差 0.005，或 RMSE 相对增加 2%；均非已批准的通用阈值，须按业务风险在最终测试前冻结。
- 样本不足、区间过宽时结论为“不确定”，不能将“没有显著差异”等同于“等效”。重复计时不增加质量样本数。

在满足质量和数据库服务约束后，再检查预定主要成本项是否有工程上有意义的改善，并列出其他成本的变化。比如候选验收门槛可以设为端到端时间减半，或 CPU-seconds 降低30%；它们是待确认的目标，不是现有实测结果，也不是允许事后挑选最有利指标的规则。

## 2. 比较对象必须是明确的软件栈

| 对象 | 默认比较职责 | 必须避免的错误 |
|---|---|---|
| openGauss-DB4AI | 原生算法、模型管理与数据库训练/预测路径 | 把不同版本XGBoost及不同模型生命周期差异全部归因于数据库内核 |
| scikit-learn + 指定估计器；Python XGBoost/LightGBM | 模型效果、同模型执行效率、现实的PG取数到批量预测pipeline | 只写“sklearn”；用手写Python逐行循环或不必要远程往返制造弱对手 |
| OpenMLDB + 明确的训练/推理模型 | 时序/关联特征、训练推理一致性、端到端SQL特征pipeline | 将特征系统当作单独分类算法，用不同下游模型的Accuracy评价数据库 |
| KumoRFM-2 | 原始关系数据上的预测质量、首次可用结果成本、重复预测成本 | 将其强制压平为同一特征表后声称检验了原生关系能力；用其他版本、Tabular模型或第三方复刻冒充v2 |
| FLAML；按需增加AutoGluon | 有限预算下的自动选模/调参效率 | 只与未经合理配置的默认模型比较，便声称AutoML优越 |

OpenMLDB 官方将其定位为训练和推理一致的特征平台，并提供搭配 LightGBM/XGBoost 的示例。[S1] KumoRFM-2 论文包含关系输入、in-context learning与fine-tuning两种使用方式。[S2] scikit-learn提供多种搜索方法；FLAML明确提供time_budget等约束。[S3][S4]

最终评测需固定：数据库版本、源码commit、模型/权重ID及hash、依赖、编译选项、设备、线程、参数、执行方式和服务版本。KumoRFM-2的ICL与微调分别成行，记录上下文样本数、构造/检索成本和可见标签。产品名称、SDK名称或同家族新模型不等于确认了所需checkpoint。

无法获得某个版本、权限、许可或运行环境时，标记“未实测/不可获取”，附原因。论文或厂商报告只能作为独立的外部参考，不能填入我们的实测表。不得擅自接受许可、上传私有数据或产生收费调用。

## 3. 两个任务口径、两个资源口径

### A. 控制变量执行轨

相同特征矩阵、划分、标签、模型族、超参数和训练预算；尽可能固定相同上游库版本与构建。用于定位执行器、SIMD、缓存、批处理、序列化等差异。库版本无法对齐时标注为软件栈比较，不作纯执行器因果归因。

### B. 真实任务端到端轨

从相同的原始数据库/数据快照、实体、目标和时间边界出发，到独立评估过且可供业务调用的pipeline或预测结果。允许各系统使用其合理的原生路径：关系模型保留关系输入，传统pipeline进行特征构建。各自必需的数据准备、上下文、特征工程、搜索和发布成本均计入对应阶段。

双轨结果分别报告，禁止将A轨驻留数组推理与B轨数据库端到端流程混为一个速度比。需要的人工准备量、特征模板与开发工作也要披露，不把给某一方精心编写的特征免费当作无人工成本。

### 资源轨

- CPU等资源轨：支持CPU的系统使用相同型号/核数/内存/并行预算，在同机顺序配对；不支持该运行模式则N/A，不按零质量或无限耗时处理。
- 原生推荐部署轨：允许各系统合理使用CPU/GPU/服务。分别报告硬件、CPU-seconds、GPU-seconds、内存、实付或明示估算费用；不能将一核CPU与一张GPU当作相同资源。

NVIDIA当前文档有可在CPU运行的Kumo Tabular示例，但它不是对KumoRFM-2可运行模式的自动确认。[S5] 不通过故意将竞品置于不支持或不合理的资源设置制造优势。

## 4. 工作负载与验证协议

保留当前小表作为开发回归集，但新增最终验收数据/任务，不能仅在开发期间反复查看过的holdout上证明新AutoML的泛化优势。

建议验收覆盖：

1. 单表分类/回归：数值与类别混合、缺失、类别不平衡、不同特征宽度。
2. 原始关系与时间任务：实体级标签、历史窗口聚合、多表join、预测未来窗口；统一可见信息、标签成熟度和时间切分。
3. 系统规模与复用：小/中/超内存工作集，源GB级到可获得的TB级；同数据上多个任务/候选、批量评分、模型切换。
4. 资源竞争：已有OLTP/OLAP负载或WAL重放下训练，检查前台p95/p99、复制延迟、预算超限与取消响应。

TB源表的小样本训练只能称为“TB源上的预算内工作集实验”。复制行、合成放大只能检验系统成本，不能当成新增独立样本或真实大数据质量证据。

预处理只在训练部分拟合。搜索/早停/校准使用验证部分；测试集不参与候选选择或决定何时停止。按实体/时间处理相关性和重复行，保留样本索引、schema、特征与变换hash。基础模型预训练重叠未知时注明，不能声称已排除污染。

质量门槛到达时间以预定验证协议中合格候选的出现时间计算，再对该候选做独立测试报告；不得在运行中观察测试分数来选“首次达标”的模型。预算不足且没有已完成候选时记为失败/未完成，不能漏掉这些任务。

## 5. 计时与资源计量

### 时间

T_end_to_end = 排队/准入 + 取数 + 特征/上下文准备 + 搜索/适配 + 独立评估 + 发布或结果写回。

模型没有fit阶段不等于没有任务准备成本。基础模型通用预训练成本不计入用户单任务成本，但上下文检索/编码、可选微调、权重加载、服务/API等待和网络传输按场景记录。

同时报告：部署准备、首次冷任务、暖任务、重复任务的摊销成本。定义连接池、进程、权重缓存、OS page cache、特征缓存的冷热状态。双方使用合理批量/向量化接口；排除部署成本的稳态测试和包含首次准备的部署测试分开。

### 资源

- 实际消耗的CPU user+system seconds与分配的核数分别报告，覆盖server、client、子进程和必要服务。不能用wall time乘配置核数伪造CPU利用量。
- 全栈峰值内存、增量内存和空闲常驻内存分开；优先容器/cgroup或声明的PSS口径，避免重复计入PG共享内存。多节点注明聚合方式。
- 实际物理I/O与逻辑读取量分别记录；临时存储峰值、持久化副本、跨进程/跨节点/离库传输字节分别记录。
- 外部托管服务不可观察的CPU/GPU/内存一律记为unknown；使用可观察的API费用与延迟，不声称其资源为零或按猜测补值。
- 同时报告总资源与相对于已有数据库空闲状态的增量。闲置CPU有机会成本，不按“免费”排除计算和数据库干扰。
- 非必要不设能耗指标；没有可信仪表时不从CPU-seconds直接捏造焦耳。
- 备机实测前须完成只读fit/主库publish及故障处理支持；不能把设计方案写成已具备能力。

不将所有成本折成一个主观加权分数。CPU、GPU、内存、I/O与时延使用各自单位；成本曲线需要折成金额时公开当次价格、时间和摊销假设。

## 6. 开发期必须留下的接口与计数

实现每个模块时回答：它支持哪个用户任务、主要改善哪个质量/成本项、可能损害什么、如何关闭并作同版本消融。

| 开发模块 | 必须可测量/验收的内容 |
|---|---|
| 预算管理/AutoML | 准入、总deadline、CPU与内存预算、实际overshoot、试验记录、最佳已完成候选、停止原因；先预留最终评估/发布成本 |
| 特征pipeline | schema和输出语义、训练拟合状态、划分绑定、权限范围、转换时间和字节、预测一致性 |
| 查询下推/复用 | 基线与优化计划、输入/输出行、源扫描次数、物化字节、缓存身份/命中、规则开关和正确性测试 |
| 训练执行 | prepare/update/evaluation/serialize等分项计时、真实轮次、峰值工作集、线程数、spill与取消检查 |
| 批量预测 | batch size、模型加载次数、吞吐、p50/p95/p99、结果物化、概率/标签一致性与数值容差 |
| 备机执行 | 只读边界、读取事务寿命、WAL冲突与取消、复制延迟、发布鉴权、主备切换清理 |
| 依赖与部署 | 必需常驻进程、启动成本、空闲内存、可选组件；不以“轻量”为由省略必要的验证 |

计数优先沿用PG/OS现有设施，昂贵profiling默认关闭，不为观察性额外建立重型常驻服务。pipeline优化必须保持NULL、行数/重复、时间、权限、类型与数值语义。每个性能特性应提供针对性测试和可回退路径；并非每个PR都运行全量竞争套件。

计划图形：质量—端到端时间曲线、质量—CPU/费用的Pareto图、规模—延迟/内存曲线、前台查询或复制干扰图。不同硬件/端点不可混成同一无说明的速度排名。各任务的质量差/归一化代价分别展示，不能平均不同单位的原始误差。

示例目标最终应写成可核查的句子：“在预先登记的X类任务、Y预算下，质量退化不超过delta，CPU消耗减少Z，并满足前台服务约束。”X/Y/delta/Z来自协议和实测，不能在结果不利时临时换任务或容差。

## 8. 执行与证据规则

现在仅固化目标，**不重跑历史基线**。开发期优先针对当前实现做正确性回归及同版本开关消融，历史数值仅作标注来源的目标参考，不能形成跨机器因果速度结论。

在核心功能达到产品里程碑、得到执行授权并冻结协议后，再进行统一竞品评测。届时为可比性需要在同机同口径重测的基线单独列明；不要将旧数据重新标为新实验。禁止把尚未开放的对手能力、计划中的API或缺失指标填成实测值。

每次正式运行保存：源码/镜像/模型hash、数据及划分hash、配置、硬件与计量口径、精确SQL/命令、逐次计时、预测、预算轨迹、退出状态和审计脚本。先定义任务范围和报告规则，再观察最终测试结果；记录所有配置和失败，额外展示部署原生强项，不人为弱化竞品。

开发验收最小检查：

- 变更对应的场景、成本假设、主要指标及回退方式已写清。
- 正确性、数据泄漏、权限和资源失败路径通过对应测试。
- 有可复算测量字段，不以实现名称或算法数量替代用户价值。
- 新依赖和常驻成本有理由；无需重型服务完成的能力不引入重型服务。
- 未实测、历史参照、同机消融、正式竞品结果严格区分。
